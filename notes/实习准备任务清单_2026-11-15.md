## 0. 本阶段的执行原则

### 核心目标

到 11 月 30 日，不要求把所有方向学透，而是完成以下求职准备闭环：

1. **岗位知识：** 能够系统讲清主流模型评测集、评测对象与方法；理解模型可解释性研究的主要问题和常见方法；能沿着真实请求链路解释 vLLM 的核心架构。
2. **BalatroEval：** 从“设计较完整的原型”推进到“规则边界可信、实验可运行、结果可分析”的评测项目。不能把尚未实现的长程规划能力写成已经验证的结论。
3. **vLLM：** 形成基于真实 vLLM 的架构理解和一份可复现的性能分析/问题定位记录，而不是只完成源码阅读笔记。
4. **求职材料：** 形成一版针对评测岗位的简历，以及两个项目的简洁、诚实、可追问的技术介绍。

- **P0：必须完成。** 直接影响项目可信度或 12 月能否开始投递。
- **P1：尽量完成。** 能明显提高岗位匹配度，但不应挤占 P0。
- **P2：暂缓。** 有价值，但本阶段不值得展开。

- 每个学习主题都必须产出一页笔记、对比表、实验或代码，不以“看完资料”作为完成标准。

- 新发现的想法先放进“暂缓列表”，不立即插入当前计划。
- 如果某项任务连续半天没有形成可检查的产物，缩小问题范围。
- 不为增加项目复杂度而加入 RL、微调或完整策略求解；当前项目重点是评测方法和可信实验。

## 1. 岗位能力补齐清单

### 1.1 现有模型评测集与 Benchmark 地图（P0）

**目标：** 建立一张“评测能力—代表性 Benchmark—评测形式—局限性”的地图，能够解释不同 Benchmark 测什么、不能证明什么。

#### A. 通用知识与推理

- [ ] MMLU / MMLU-Pro：学科知识与复杂问题回答；理解题目难度、选项形式和数据污染风险。
- [ ] GPQA：高难度科学问题；理解专家级题目与普通知识问答的区别。
- [ ] BIG-bench / BBH：多任务能力集合；理解任务覆盖面与单项分数的局限。
- [ ] GSM8K / MATH：数学推理；区分答案正确率与推理过程质量。
- [ ] ARC、HellaSwag 等传统基准：了解其历史作用和当前区分能力局限。

#### B. 代码能力

- [ ] HumanEval / MBPP：函数级代码生成与 pass@k。
- [ ] LiveCodeBench：理解动态更新、减少静态数据污染的思路。
- [ ] SWE-bench：理解真实仓库 issue 修复、测试验证和 Agent 执行环境的要求。

#### C. 指令遵循、对话与偏好

- [ ] IFEval：可验证指令约束的遵循情况。
- [ ] MT-Bench：多轮对话评测与 LLM-as-a-Judge 的基本思路及偏差。
- [ ] Arena-Hard：偏好比较式评测；理解胜率、配对比较和评审模型偏差。
- [ ] AlpacaEval：理解自动评审、长度偏差和评审器校准问题。

#### D. 长上下文、工具使用与 Agent

- [ ] LongBench / RULER：长上下文任务覆盖和长度外推问题。
- [ ] BFCL：函数调用/工具调用能力，关注参数、格式、执行正确性。
- [ ] τ-bench：理解面向真实任务流程的工具使用与交互式评测。
- [ ] AgentBench 等 Agent 基准：了解环境交互、任务完成、轨迹和成本等维度。

#### E. 多模态

- [ ] MMMU：多学科、多模态理解。
- [ ] MathVista：视觉数学推理。
- [ ] OCRBench：文字识别与文档视觉理解。
- [ ] Video-MME：视频理解及长视频评测问题。

#### 每个 Benchmark 至少记录

- [ ] 评测对象：模型本身、模型+提示词、模型+工具，还是完整 Agent 系统？
- [ ] 能力维度：知识、推理、遵循、生成、感知、工具使用、长期任务等。
- [ ] 数据形式：选择题、开放式答案、代码执行、环境交互、多模态输入。
- [ ] 评分方式：Exact Match、Accuracy、pass@k、Judge、Pairwise Win Rate、任务成功率等。
- [ ] 可复现性：是否有标准答案、执行环境、评审器、随机性控制？
- [ ] 主要局限：数据污染、题目难度饱和、评审偏差、提示词敏感、训练集泄漏、生态偏差等。

**交付物：** `Benchmark_Map.md`，建议控制在 3—5 页。不要写成每个数据集的百科全书。

### 1.2 评测对象、方法与指标（P0）

**目标：** 能够从“测什么、怎么测、如何判断差异可信”三个层次设计评测。

#### 评测对象

- [ ] Base Model：预训练模型的知识、推理、语言建模及泛化能力。
- [ ] Post-trained Model：指令遵循、对话质量、安全性、偏好对齐。
- [ ] Tool-use Model / Agent：工具选择、参数构造、执行结果、状态管理、任务完成率。
- [ ] Multimodal Model：图像、视频、音频及跨模态理解。
- [ ] Inference System：延迟、吞吐、显存、稳定性、并发能力。
- [ ] Checkpoint / Training Stage：不同训练阶段或 checkpoint 的能力变化、收益和退化。

#### 评测方法

- [ ] 静态基准：固定数据集、固定提示词、固定评分程序。
- [ ] 动态/在线基准：动态题目、持续更新、减少污染。
- [ ] 执行式评测：代码运行、工具调用、环境交互、测试用例。
- [ ] LLM-as-a-Judge：评审提示词、位置偏差、长度偏差、评审器一致性。
- [ ] Pairwise Evaluation：成对比较、胜率、平局处理和统计检验。
- [ ] Human Evaluation：人工标注规范、一致性和成本。
- [ ] Robustness Evaluation：提示词扰动、格式变化、分布外样本和重复运行。
- [ ] Regression Evaluation：checkpoint 对比、能力退化检测、版本回归。

#### 指标与统计

- [ ] Accuracy / Exact Match：适用于有确定答案的任务。
- [ ] pass@k：理解代码生成中至少一次通过的估计含义。
- [ ] Win Rate / Pairwise Preference：理解比较式评测的统计含义。
- [ ] Task Success Rate：适用于 Agent/环境交互任务。
- [ ] Tool Call Accuracy、参数正确率、执行成功率：拆分工具调用链路错误。
- [ ] Latency、Throughput、TTFT、TPOT：区分服务性能指标。
- [ ] Confidence / Calibration：区分模型置信度和真实正确率。
- [ ] Bootstrap Confidence Interval：理解区间估计。
- [ ] McNemar：理解配对二分类结果的比较。
- [ ] Wilcoxon Signed-Rank：理解配对、非参数比较。
- [ ] Multiple Testing / Holm：理解多重比较校正。
- [ ] Pass^k / 多次运行稳定性：明确聚合方式和失败概率的解释边界。

**交付物：** `Eval_Methods_and_Metrics.md`，包含一张评测设计流程图：目标定义 → 数据/场景 → 执行协议 → 评分 → 统计 → 误差分析 → 结论边界。

### 1.3 模型可解释性与行为分析（P1）

**目标：** 先区分行为层面的可解释分析与机制可解释性，不把 Trace 分析夸大成“理解模型内部机理”。

#### 第一层：行为与输出分析（当前项目可落地）

- [ ] 阅读模型输出、工具调用和 Agent Trace 的常见分析方式。
- [ ] 学习错误分类：知识错误、推理错误、指令遵循错误、工具选择错误、参数错误、状态跟踪错误、规划错误。
- [ ] 学习按能力切片、错误聚类、反事实对照和最小失败案例分析。
- [ ] 在 BalatroEval 中分析决策错误、非法动作、资源分配错误和失败恢复问题。
- [ ] 探索模型置信度/Logits 与决策质量（如 Regret）之间的相关性；明确相关性不等于因果解释。

#### 第二层：模型内部机制研究（建立概念地图）

- [ ] Probing：用线性探针等方法分析隐藏状态中是否包含某类信息。
- [ ] Logit Lens：观察中间层表示映射到词表后的预测变化。
- [ ] Attention Analysis：理解注意力权重可视化的用途与局限，不能简单等同于解释。
- [ ] Activation Patching / Causal Intervention：通过干预激活研究组件对行为的因果影响。
- [ ] Causal Tracing：理解信息路径追踪的基本思想。
- [ ] Sparse Autoencoders（SAE）：了解稀疏特征分解和特征解释的基本思路。
- [ ] 了解 mechanistic interpretability 与 post-hoc explanation 的区别。

**交付物：** `Interpretability_Notes.md`，至少回答：
1. 行为可解释性和机制可解释性有什么区别？
2. 哪些结论可以从 Trace 得出，哪些不能？
3. 如果研究模型为什么做出某个错误决策，下一步需要什么内部信号或干预实验？

**边界：** 本阶段不要求复现 SAE、训练探针或做完整机制解释研究。先建立准确概念，再判断是否值得深入。

### 1.4 vLLM 架构知识（P0）

**目标：** 能够沿着一次请求的真实执行路径解释 vLLM，而不是按目录逐文件阅读。

#### 核心请求链路

- [ ] API Server：请求接入、参数处理、流式响应。
- [ ] Engine / Async Engine：请求如何进入推理引擎。
- [ ] Scheduler：等待队列、运行队列、调度策略和批处理。
- [ ] Model Runner：模型执行、Prefill 与 Decode。
- [ ] KV Cache：分配、复用、释放和显存管理。
- [ ] Sampling：采样参数如何影响生成。
- [ ] Worker / Distributed Execution：理解单卡与多卡执行边界。

#### 必须理解的核心机制

- [ ] PagedAttention 的问题背景、逻辑块/物理块和内存管理思路。
- [ ] Continuous Batching 与传统静态 Batch 的区别。
- [ ] Prefill / Decode 阶段的计算特征。
- [ ] KV Cache 的显存占用、碎片和吞吐影响。
- [ ] Chunked Prefill、Prefix Caching 等机制的作用场景。
- [ ] Tensor Parallel 等并行方式的基本概念。
- [ ] TTFT、TPOT、吞吐、显存利用率和并发数之间的权衡。

#### 实验与定位

- [ ] 固定模型、硬件、输入长度、输出长度和并发条件。
- [ ] 测量 TTFT、TPOT、吞吐和显存占用。
- [ ] 至少比较两组有意义的配置（例如并发数、批处理相关参数或输入长度）。
- [ ] 解释结果变化来自调度、Prefill、Decode 还是 KV Cache 压力。
- [ ] 保存命令、环境、配置、原始结果和分析。

**交付物：** `vLLM_Architecture_Notes.md` + 一份可复现的性能实验记录。若时间不足，优先保证链路图和一组可信实验，不追求改造核心引擎。

## 7. 最终执行顺序

如果时间紧张，严格按以下顺序取舍：

1. **先保证 BalatroEval 的规则和 Oracle 可信。** 评测系统本身不可信，后面的模型排名和分析都没有意义。
2. **再跑通最小端到端评测闭环。** 少量高质量场景优先于未经验证的 60 个场景。
3. **补齐 Benchmark 与评测方法地图。** 这是两个目标岗位共同要求的知识基础。
4. **完成 vLLM 主链路和一组可复现实验。** 以工程理解和性能分析为目标，不追求源码覆盖率。
5. **学习可解释性并保持结论边界。** 先掌握概念与方法，再决定是否做小实验。
6. **11 月底开始以现有证据投递。** 不必等所有计划全部完成；简历必须准确区分已完成、进行中和计划中。

**本阶段的判断标准不是“学了多少”，而是：能否拿出可信的项目证据，能否解释评测设计的取舍，能否对实验结果和结论边界负责。**
